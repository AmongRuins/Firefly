在进行需求分析过后，就是测试计划阶段，这里有些公司可能会先进行测试计划阶段。

测试计划阶段由测试项目负责人和组长去规范大概这个项目需要多少时间，每个阶段需要完成什么，每个人需要完成哪些模块，需要用到什么工具等关于时间人力的安排。

---

## 测试用例是什么

**测试用例**是软件测试活动的最小执行单元，是为验证软件某一特定功能、性能、安全性等需求是否符合预期，预先设计的一套包含`测试场景、输入数据、执行条件、操作步骤、预期结果`的标准化文档。它是测试执行的核心依据，也是保障测试覆盖度、可追溯性、缺陷可复现性的关键载体。

### 标准测试用例核心构成要素
| **要素名称**  | **核心说明**                                      | **是否必填** |
|-----------|-----------------------------------------------|----------|
| **用例 ID** | 唯一标识，便于管理追溯，通用格式：模块 - 功能 - 序号（如 LOGIN-P0-001） | 是        |
| **用例标题**  | 一句话清晰描述测试目标，无歧义（如 “验证正确账号密码可正常登录系统”）          | 是        |
| **所属模块**  | 归属的产品功能模块（如 “用户登录模块”）                         | 是        |
| **前置条件**  | 执行用例前必须满足的环境 / 数据要求（如 “系统可正常访问、测试账号已注册”）      | 是        |
| **测试步骤**  | 分步执行的操作，必须清晰、可复现，无模糊表述                        | 是        |
| **输入数据**  | 执行步骤中需要输入的参数（如账号、密码、数值），无输入则填 “无”             | 是        |
| **预期结果**  | 每一步操作对应的系统预期表现，是判断用例是否通过的唯一标准                 | 是        |
| **用例优先级** | 划分执行优先级，通用规则 P0（核心）- P3（边缘），P0 为冒烟测试必测项        | 是        |
| **测试类型**  | 标注用例归属类型（如功能测试、性能测试、安全测试、兼容性测试）               | 是        |
| **实际结果**  | 执行后系统的真实表现，测试执行阶段补充                           | 否        |
| **测试结论**  | 用例执行结果：通过 / 不通过 / 阻塞 / 未执行，测试执行阶段补充           | 否        |
| **备注**    | 特殊说明、缺陷关联、环境依赖、异常场景补充                         | 否        |

一般核心主流程或者用作冒烟用例的其优先级为 P0，其余一般流程，异常流程的为P1，最低的则是界面、兼容这方面的测试。

### 核心原则

1. **原子性**：`一条用例仅验证一个核心测试点`，避免多功能耦合，便于缺陷定位。
2. **可复现性**：任何人拿到用例，都能按步骤`复现`完全一致的测试过程与结果，无歧义。
3. **覆盖全面**：覆盖正常场景、异常场景、边界场景、合规场景，不遗漏需求点。
4. **优先级清晰**：核心功能、高频用户场景优先保障，适配冒烟、回归、全量测试不同场景。
5. **可维护性**：结构规范、命名统一，需求变更时可快速迭代调整。
