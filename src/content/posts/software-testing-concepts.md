## 什么是软件

软件的定义：一个计算机程序，包含其所用的数据和有关文档资料的集合。（`软件 = 程序 + 数据 + 文档`）

软件可分为两大类：
- **系统软件**：是生成、准备和执行其他程序所需要的一组文件和程序。例如操作系统、数据库、驱动程序、java编译环境等。
- **应用软件**：计算机用户为了解决某些具体问题而购买、开发和研制各种程序或软件包。例如手机上的App、电脑上的应用程序等。

### 两种架构

1. **CS 架构（客户端 / 服务器架构）**：需要安装定制的客服端程序，每次更新客服端和服务器都需要同步更新。
2. **BS 架构（浏览器 / 服务器架构）**：只需要一个浏览器用户就能访问服务器的数据，每次更新只需要服务器更新即可，部署维护成本极低。

## 什么是软件测试

软件测试的定义：1983 年，IEEE 就提出软件工程的标准术语，他将**软件测试定义**为：使用`人工和自动`手段来运行或测试某个系统的过程，其**目的**在于检验它`是否满足规定的需求（规格说明书）`或`弄清预期结果和实际结果之间的差别`。

我们为什么要做软件测试？它的目的是什么？
1. 软件测试为了发现程序(软件)存在的代码或业务逻辑错误。（`发现bug，降低成本`）
2. 软件测试为了检验产品是否符合用户需求。（`保证产品质量`）
3. 软件测试为了提高用户的体验。（`提高用户体验度`）

## 软件测试分类

### 按阶段划分

1. **单元测试**：以开发人员为主测试`软件最小可测试单元`，包括函数、方法、类、独立业务模块、单个程序组件，用以验证`单元内部的逻辑正确性`，全覆盖代码分支、边界条件、异常处理场景，在编码阶段就拦截语法、逻辑类底层缺陷。
2. **集成测试**：以测试人员为主测试多个单元模块组装后的子系统、`模块间的接口与数据交互`、系统的第三方组件/中间件/外设的集成链路，用以验证`模块间的接口调用`、数据传递是否符合需求，解决模块间的兼容性、协同工作异常，发现集成链路中的缺陷。
3. **系统测试**：全权由测试人员测试`完整集成后的软件系统`、配套软硬件环境、相关文档、上下游关联系统，完全模拟用户真实生产环境，用以端到端验证`整个软件系统是否完全满足需求规格的所有要求`，保证软件的质量。
4. **验收测试**：由用户/甲方为主，产品负责人/测试工程书提供辅助支持，以证软件`是否符合业务使用需求`、是否达到验收标准，最终决定是否接收该软件。
    
    完全基于业务场景，不关注技术实现细节，核心分为 3 类细分形式：
    - UAT 测试（用户验收测试）：`甲方 / 业务方主导的核心验收环节`，是国内项目交付最主流的验收形式。
    - Alpha 测试（内测）：在开发 / 测试环境，由内部用户 / 核心客户开展的`封闭验收测试`。
    - Beta 测试（公测）：在生产环境，由`海量真实终端用户`开展的公开验收测试，常用于互联网产品。

---

### 按是否查看代码划分

1. **黑盒测试**：将软件视作一个完全看不到内部结构的 “黑盒子”，`完全不关注代码实现、逻辑流程、底层架构，仅站在用户视角`，验证软件的输入与输出是否符合需求规格，核心判断 “软件能不能做该做的事”。
2. **白盒测试**：完全打开软件的 “盒子”，`全面查看、深度分析源代码的内部结构、逻辑分支、执行路径、数据流转、异常处理`，基于代码实现细节设计测试用例，核心验证 “代码写得对不对，有没有按设计要求执行”。
3. **灰盒测试**：结合黑盒与白盒的核心优势，以`黑盒的业务功能验证为核心，辅以部分源代码 / 接口文档的查看与分析`，既关注输入输出是否符合需求，也会重点验证核心链路的模块交互、接口调用、数据流转，不做全量代码级的深度覆盖，核心验证 “模块间能不能协同做好该做的事”。是当前分布式、微服务架构下最主流的测试模式之一。

---

### 按是否运行代码划分

1. **静态测试**：不启动、不运行被测软件 / 程序代码，仅通过人工或自动化工具，对`全生命周期的文档、代码、设计文件开展评审、检查、分析`的测试方式。
2. **动态测试**：实际`运行被测软件 / 程序`，在指定的运行环境中输入测试用例，比对实际输出与预期结果的差异。

### 按测试手段划分

1. **手工测试**：以测试人员为唯一执行主体，通过`人工模拟用户操作`、逐行执行测试逻辑、人工比对实际结果与预期结果、记录并定位缺陷的测试手段。
2. **动态测试**：通过`编写自动化测试脚本`、借助`自动化测试工具 / 框架`，替代人工自动完成用例执行、结果比对、报告生成、缺陷预警全流程的测试手段。

### 按测试包含的内容划分

1. **功能测试**：功能是否符合需求。
2. **界面测试**：查看 UI 布局。
3. **安全测试**：例如防止 SQL 注入，一般由高级测试工程师进行。
4. **兼容性测试**：不同浏览器 / 手机系统下软件的运行状态。
5. **易用性测试**：用户上手难度是否简单。
6. **性能测试**：并发下系统是否能正常运行。

一般测试人员除安全测试外，其余测试都需要掌握。

### 其他划分

1. **冒烟测试**：在系统测试前，针对`软件核心主干功能`的快速验证，是进入全量测试的前置准入环节，仅`验证登录`、`核心业务流转`等阻塞性场景，确认版本可测性。
    
    对于`非主干的小缺陷`（如文案错误、样式偏差）不影响可测试性，无需打回版本，可在正式测试中同步提报。
2. **回归测试**：在`缺陷修复`、`版本迭代`后，验证原有功能是否正常、缺陷是否彻底修复、是否引入新的功能问题。
    
    回归测试在时间不充裕的情况下，一般仅测试`与缺陷修复相关联的场景`。
3. **探索性(随机)测试**：无预设固定用例，基于`测试人员的业务经验与测试思维`，自由设计测试场景、同步执行与发现缺陷，挖掘需求覆盖外的隐藏功能问题。
