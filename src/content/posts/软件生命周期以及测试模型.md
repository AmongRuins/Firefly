## 测试模型

1. 瀑布模型

按照**固定的流程**（`单向、顺序、不可逆`）顺序执行：需求 → 设计 → 开发 → 测试 → 维护 → 退役

该模型的特点是将测试放在最后，唯有前面做完轮到测试才测，且要求的文档多，通过**文档传递需求、设计、标准**给下一个人

该模型**结构清晰、阶段明确、文档齐全、适合需求稳定**，但发现 Bug 会很晚，从而导致修复成本高，也很难变更需求，迭代不了，风险相对集中，上线压力会很大

2. V 模型

该模式的核心思想让测试早点介入，分级对应、预防缺陷，比如左边（开发）—— 右边（测试）
- 需求分析 ↔ 验收测试
- 概要设计 ↔ 系统测试
- 详细设计 ↔ 集成测试
- 编码 ↔ 单元测试

该模型的特点是测试和开发**同步设计**（不是最后才测），分阶段测试，层次清楚，文档适中

该模型提早设计测试用例、定位 Bug 准、阶段清晰，但不适合**需求频繁变动**、不能迭代

3. 增量模型 & 迭代模型

增量模型的思路是**先做核心功能 → 做完测完 → 再加次要功能 → 再测**，而迭代模型的思路则是**先做完整简易版 → 测 → 修改优化 → 第二版 → 第三版**

增量模型像拼积木那样**分模块交付**，而迭代模型则**每次都是完整系统**，只是越来越好

增量模型先上线基础版，后面慢慢加功能，优点在于早期能用、风险小，但模块之间容易兼容、接口有问题

迭代模型允许改需求、反复优化，这样适合需求不确定、灵活、发现问题早，但次数多、管理会变复杂

3. w模型

由两个 V 并排组成，像 W，它的核心思想是**测试 与 开发 同步开始、并行进行**、**全过程测试（每个阶段都有测试）**以及**测试独立**，不依附开发

比如左边（开发）—— 右边（测试）
- 需求分析 → 测试需求
- 概要设计 → 测试概要设计
- 详细设计 → 测试详细设计
- 编码 → 单元 / 集成测试
- 上线 → 系统 / 验收测试

虽然这种模型能尽早发现缺陷，成本低，过程可控，质量高，分工清楚，测试独立，但相对的不支持变更、不支持迭代，也不适合需求经常变、快速开发

4.  敏捷模型（现在最常用）

该模型核心思想是`小步快跑、快速迭代、持续交付、拥抱变化、注重沟通`，其特点为：
- 周期短（2～4 周一个迭代 /sprint）
- **人为主、沟通多、文档少**
- 边开发、边测试、边修改
- 适合**需求经常变更**的项目
- 持续测试、持续上线

该模型流程是`拆分需求 → 一个迭代做完 → 测试 → 交付 → 下一轮优化`，其**适应变化快、见效快、问题发现早、用户体验好**，但也存在**文档少、依赖人、管理难、容易乱**的缺点

敏捷开发对于需求经常变更的项目，能够做到边开发、边测试、边修改，问题能早点发现，并持续测试，持续上线。
