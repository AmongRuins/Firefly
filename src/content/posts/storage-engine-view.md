## 存储引擎

查看 MySQL 实例支持的所有存储引擎
```sql
-- 结果中Support列标注DEFAULT的，就是实例的默认存储引擎。
SHOW ENGINES;
```

### InnoDB（MySQL 5.5+ 默认引擎，绝对主流）

InnoDB 是 MySQL 官方`主推的事务型引擎`，覆盖了 99% 的生产业务场景（`需要数据可靠性、高并发读写、事务支持的业务场景`）。
| **优点**                | **缺点**                     |
|-----------------------|----------------------------|
| 数据可靠性拉满，支持事务和崩溃恢复 | 相比 MyISAM，有事务开销，占用存储空间更大   |
| 高并发读写性能优异，行级锁冲突少  | 维护复杂度更高，需要合理配置缓冲池、日志等参数    |
| 支持外键、MVCC，功能最全面   | 批量写入的纯读场景，性能略低于优化后的 MyISAM |

### MyISAM（MySQL 5.5 之前默认引擎，已基本淘汰）

MyISAM 是 MySQL `早期`的默认引擎，设计简单，无事务支持，现在已被 InnoDB 全面替代。
| **优点**                  | **缺点**          |
|-------------------------|-----------------|
| 设计简单，维护成本低          | 不支持事务，数据可靠性极差   |
| 纯读场景（无写入）性能优异，占用空间小 | 表级锁，写并发性能几乎为零   |
| 支持全文索引、压缩表          | 宕机后数据易损坏，无法自动恢复 |

MySQL 8.0 已逐步移除对 MyISAM 的支持，且 InnoDB 现已原生支持全文索引，MyISAM 已无不可替代的优势。

### 相关存储引擎对比

| **对比维度**  | **InnoDB**         | **MyISAM**   | **Memory**  | **Archive** |
|-----------|--------------------|--------------|-------------|-------------|
| **事务支持**  | ✅ 完整 ACID          | ❌ 不支持        | ❌ 不支持       | ❌ 不支持       |
| **锁粒度**   | 行级锁 + 间隙锁          | 表级锁          | 表级锁         | 行级锁         |
| **崩溃恢复**  | ✅ 原生支持             | ❌ 不支持        | ❌ 数据全丢      | ❌ 不支持       |
| **外键约束**  | ✅ 支持               | ❌ 不支持        | ❌ 不支持       | ❌ 不支持       |
| **索引能力**  | 聚簇索引 + 二级索引，支持全文索引 | 非聚簇索引，支持全文索引 | 哈希 / B 树索引  | 仅自增主键索引     |
| **数据持久化** | ✅ 磁盘持久化            | ✅ 磁盘持久化      | ❌ 内存存储，重启丢失 | ✅ 磁盘压缩持久化   |
| **存储占用**  | 中等                 | 偏小           | 内存占用高       | 极小          |
| **核心优势**  | 高可靠、高并发、功能全        | 纯读性能好、占用小    | 极致读写速度      | 高压缩、高写入性能   |

## 视图

视图（View） 是一种`虚拟表`，其内容`由查询定义`。它本身`不存储数据`，数据来自底层的基表（Base Table），使用时动态从基表查询生成。

**视图的核心作用**：
- **简化复杂查询**：将多表关联、子查询等复杂逻辑封装成视图，直接查询视图即可。
- **数据安全**：限制用户只能访问视图中的字段 / 行，隐藏基表的敏感数据。
- **逻辑独立性**：基表结构变化时，只需修改视图定义，无需修改应用代码。

**创建视图**
```sql
CREATE VIEW 视图名 AS
SELECT 字段1, 字段2 FROM 基表 WHERE 条件;
```

**修改视图**
```sql
-- 方式1：覆盖创建（推荐）
CREATE OR REPLACE VIEW 视图名 AS SELECT ...;
-- 方式2：ALTER修改
ALTER VIEW 视图名 AS SELECT ...;
```

**删除视图**
```sql
DROP VIEW IF EXISTS 视图名;
```

使用视图：`像普通表一样查询`
```sql
SELECT * FROM 视图名;
```

注意事项：
- **更新限制**：若视图包含 `GROUP BY`、聚合函数（`SUM/COUNT`）、`DISTINCT` 等，则无法通过视图更新基表数据。
- **性能影响**：视图是 “`实时查询`”，复杂视图（视图套视图）可能影响性能，需合理设计。
- **视图不存储数据**：视图是虚拟表，数据全部来自底层基表。基表数据更新，视图的查询结果会同步变化。
- **权限控制最佳实践**：给业务用户仅开放视图的查询权限，不开放基表的访问权限，实现数据隔离和敏感信息保护。

## MySQL用户管理

针对 root 外的用户，可以通过如下命令：
```sql
-- 创建一个用户
CREATE USER '用户名'@'IP位置' IDENTIFIED BY '密码';

-- 删除一个用户
DROP USER '用户名'@'IP位置';

-- 修改自已密码
SET PASSWORD = PASSWORD('密码');
```

## MySQL权限

MySQL 权限的本质是：`谁（用户）能从哪台机器（主机），对什么数据库对象，执行什么操作`。
> 核心规则：MySQL 的用户唯一标识是 `用户名@主机地址`，而非单纯的用户名。

MySQL 验证权限时，`先匹配最精确的主机地址，再按「全局→库→表→列」的范围从大到小匹配`，只要任意一个级别有权限，即可生效。
- `root@localhost`：仅允许本地登录的 root 用户
- `root@192.168.1.%`：仅允许从 192.168.1.0/24 内网网段登录的 root 用户
- `root@%`：允许从任意地址远程登录的 root 用户

所有权限都存储在 `mysql` 系统库的权限表中，无需手动修改，通过标准命令操作即可：
| **权限表**                | **存储内容**         | **权限级别**    |
|------------------------|------------------|-------------|
| **mysql.user**         | 用户基础信息、全局权限      | 全局级别（.）     |
| **mysql.db**           | 单库全表权限           | 数据库级别（db.*） |
| **mysql.tables_priv**  | 单表权限             | 表级别（db.tbl） |
| **mysql.columns_priv** | 单列权限             | 列级别         |
| **mysql.procs_priv**   | 存储过程 / 函数 / 视图权限 | 子程序级别       |

### 权限级别

| **权限级别**  | **范围写法**           | **适用场景**                              |
|-----------|--------------------|---------------------------------------|
| **全局级别**  | *.*                | DBA 管理员账号，对整个 MySQL 实例生效，禁止给业务账号使用    |
| **数据库级别** | db_name.*          | 线上业务核心场景，给应用账号仅开放对应业务库的权限             |
| **表级别**   | db_name.table_name | 精细化控制，比如仅允许操作订单表，禁止访问用户敏感表            |
| **列级别**   | 单独指定字段             | 敏感数据管控，比如仅允许查看员工姓名 / 部门，禁止查看薪资 / 身份证号 |
| **子程序级别** | 存储过程 / 函数名         | 控制存储过程的执行、修改权限                        |

### 常用权限

1. 数据操作类（DML，业务账号核心权限）

| **权限**     | **用途**         |
|------------|----------------|
| **SELECT** | 查询数据，只读账号必备    |
| **INSERT** | 插入数据           |
| **UPDATE** | 更新数据           |
| **DELETE** | 删除数据（线上业务谨慎授予） |

2. 结构操作类（DDL，仅给开发 / 管理员，禁止给线上业务账号）

| **权限**                             | **用途**                 |
|------------------------------------|------------------------|
| **CREATE**                         | 创建数据库、表、索引             |
| **DROP**                           | 删除数据库、表、视图（高危，禁止给业务账号） |
| **ALTER**                          | 修改表结构、索引（高危，禁止给线上业务账号） |
| **INDEX**                          | 创建 / 删除索引              |
| **CREATE VIEW / SHOW VIEW**        | 创建 / 查看视图定义            |
| **CREATE ROUTINE / ALTER ROUTINE** | 创建 / 修改 / 删除存储过程 / 函数  |
| **EXECUTE**                        | 执行存储过程 / 函数            |

3. 管理类权限（仅给 DBA，绝对禁止给普通业务账号）

| **权限**                                     | **用途**                    | **风险等级**    |
|--------------------------------------------|---------------------------|-------------|
| **ALL PRIVILEGES**                         | 除GRANT OPTION外的所有权限，简写ALL | 高           |
| **CREATE USER**                            | 创建、删除、修改用户的权限             | 高           |
| **GRANT OPTION**                           | 将自身权限授予其他用户的权限，可导致权限失控    | 极高          |
| **SUPER**                                  | 超级管理员权限，可终止线程、修改全局变量、配置主从 | 极高          |
| **REPLICATION SLAVE / REPLICATION CLIENT** | 主从复制专用权限                  | 中           |
| **SHOW DATABASES**                         | 查看所有数据库名的权限               | 中           |
| **FILE**                                   | 读取 / 写入服务器本地文件，可直接获取系统权限  | 极高，生产环境严禁授予 |

### 命令操作

执行以下命令，必须使用拥有 `CREATE USER` 和 `GRANT OPTION` 权限的账号（默认 root 账号）。

创建用户：MySQL 8.0+ 必须先创建用户，再授权，不支持 `GRANT` 隐式创建用户，否则会直接报错。
```sql
-- 标准语法
CREATE USER '用户名'@'主机地址' IDENTIFIED BY '强密码';

-- 示例1：创建仅本地登录的业务账号
CREATE USER 'app_user'@'localhost' IDENTIFIED BY 'App@Pass2026';

-- 示例2：创建仅内网网段登录的只读账号
CREATE USER 'read_user'@'192.168.1.%' IDENTIFIED BY 'Read@Only2026';

-- 示例3：创建开发环境测试账号（生产环境禁止使用@%）
CREATE USER 'test_user'@'%' IDENTIFIED BY 'Test@Pass2026';
```

授权操作（GRANT）：`WITH GRANT OPTION` 会让该用户可将自身权限授予他人，仅管理员使用，绝对禁止给业务账号。
```sql
-- 标准语法
GRANT 权限1,权限2 ON 权限范围 TO '用户名'@'主机地址';

-- 示例1：线上业务标准配置：给应用账号授予业务库读写权限（最常用）
GRANT SELECT,INSERT,UPDATE,DELETE ON shop_db.* TO 'app_user'@'192.168.1.%';

-- 示例2：给只读账号授予全库查询权限（报表/数据分析用）
GRANT SELECT ON *.* TO 'read_user'@'192.168.1.%';

-- 示例3：给开发账号授予测试库全权限（仅开发环境用）
GRANT ALL ON test_db.* TO 'dev_user'@'192.168.1.%';

-- 示例4：列级精细化授权：仅允许查看员工表的非敏感字段
GRANT SELECT(emp_id,emp_name,dept_name) ON company_db.employee TO 'hr_read'@'192.168.1.%';

-- 示例5：视图专用授权
GRANT CREATE VIEW,SHOW VIEW,SELECT ON shop_db.* TO 'app_user'@'192.168.1.%';
```

查看当前用户权限
```sql
-- 查看当前登录用户的权限
SHOW GRANTS;

-- 查看指定用户的完整权限（最常用）
SHOW GRANTS FOR 'app_user'@'192.168.1.%';

-- 查看实例所有用户的基础信息（用户名+允许登录的主机）
SELECT user,host FROM mysql.user;
```

撤销权限（REVOKE）：撤销的`权限范围、权限列表必须和授权时完全一致`，否则无法正确撤销。
```sql
-- 标准语法
REVOKE 权限1,权限2 ON 权限范围 FROM '用户名'@'主机地址';

-- 示例1：撤销业务账号的DELETE权限，防止误删数据
REVOKE DELETE ON shop_db.* FROM 'app_user'@'192.168.1.%';

-- 示例2：撤销用户的所有权限
REVOKE ALL PRIVILEGES, GRANT OPTION FROM 'test_user'@'%';
```

删除用户：不要直接用 DELETE 删除 mysql.user 表的数据，会导致权限残留、数据库异常。
```sql
-- 标准语法（全版本推荐，无权限残留）
DROP USER '用户名'@'主机地址';

-- 示例
DROP USER 'test_user'@'%';
```

### 变化注意

MySQL 8.0 权限核心发生变化：
1. **移除 GRANT 隐式创建用户功能**：5.7 支持 `GRANT ... ON ... TO 'user'@'%' IDENTIFIED BY 'xxx'` 同时创建用户和授权，8.0 该写法会直接报错，必须先 CREATE USER 再授权。

2. **新增角色（Role）功能**：可将一组权限打包成角色，批量给用户授权，修改权限时仅需修改角色，无需逐个调整用户，适合多账号统一管理。
```sql
-- 角色示例：创建只读角色，批量授权给多个用户
CREATE ROLE 'shop_read_role';
GRANT SELECT ON shop_db.* TO 'shop_read_role';
GRANT 'shop_read_role' TO 'read_user1'@'192.168.1.%', 'read_user2'@'192.168.1.%';
-- 设置用户登录后自动激活角色
SET DEFAULT ROLE 'shop_read_role' TO 'read_user1'@'192.168.1.%';
```

3. **密码策略默认开启**：默认启用密码复杂度校验，强制使用强密码，禁止弱密码。

4. **移除PASSWORD()函数**：修改密码必须使用 `ALTER USER 'user'@'%' IDENTIFIED BY '新密码';`。

5. 细粒度权限拆分：拆分了原 `SUPER` 权限，新增 `SESSION_VARIABLES_ADMIN`、`SYSTEM_USER` 等细分权限，安全性更高。
